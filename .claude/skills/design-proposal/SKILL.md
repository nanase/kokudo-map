# design-proposal — 実装前に設計の要点で yes/no をもらう

設計が固まった後、実装に時間をかける前に、後戻りしにくい判断だけを人に見せて方針違いを拾う。人が 30 秒で yes/no を返せる粒度に絞る。実作業（設計の確定・実装）はしない。

設計意図（データモデル・API 形・不可逆マイグレーション）の良し悪しは test も AI レビューも判定できない。だから設計段にこの人ゲートを 1 つ置く。実装段には足さない。

## 発動するか — 選んだ判断があるときだけ

設計の中身でなく、選択肢があって片方を選んだ判断があるかで決める。

- 選んだ判断が 1 つ以上ある → 発動して要約を出す
- 仕様どおり・唯一解・既存実装に倣うだけ・些細（変数名・配置） → 発動しない
  - 一行 FYI に留める
- 迷ったら発動させない

## 要約のしかた

選んだ判断だけを 2〜5 個、不可逆性の高い順に 1 行ずつ並べる。各行に「選んだ案／一言理由／却下案」を入れる。設計の全体は説明しない。

うち間違うと最も損する 1 つを強調する。後戻りが既存データ・他コード・マイグレーションを巻き込む判断（PK 型・正規化・FK・公開 API の形）が候補となる。局所的に直せる判断は強調しない。

## 提示テンプレート

`AskUserQuestion` で尋ねる。原則は yes/no の 1 問とする。各問は二択にする。重い問い・多数の問いは避ける。

```text
設計が固まりました。実装前に、選んだ判断だけ確認させてください。

- 【最重要】<選んだ案> ／ <一言理由> ／ 却下: <却下案>
- <選んだ案> ／ <一言理由> ／ 却下: <却下案>

このまま実装へ進めてよいですか。
```

選択肢は「このまま実装へ（既定）」と「直したい（どこを直すか指定）」の二つとする。

## 出力

- このまま実装へ → 呼び出し元へ「承認・実装へ進む」を返す
  - 以後何もしない
- 直したい → 指定された直し内容を返す
  - 曖昧なら 1 度だけ聞き返す
