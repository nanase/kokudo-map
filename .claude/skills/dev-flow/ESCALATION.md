# エスカレーション境界

AI が確認なしで進めてよい範囲と、必ず停止して人に確認する範囲を定める。自走の安全弁である。

- 要件を受けたら原則として自走
  - 確認は例外
- ただし下記の停止条件（STOP）に 1 つでも触れる判断は、実行する前に必ず停止して確認
- STOP か PROCEED か迷ったら STOP を選ぶ
  - 安全側に倒す

## 必ず停止して確認する（STOP）

### 1. 取り返しのつかない操作

| 対象 | 例 |
|------|----|
| 本番反映・デプロイ | 本番環境へのリリース、本番設定の変更 |
| 本番データの破壊・不可逆変換 | データ削除、破壊的マイグレーション、上書き |
| 外部への送信・公開 | メール送信、外部 API への本番リクエスト、第三者への公開 |
| git 履歴の破壊 | force-push、ブランチ削除、保護ブランチ（main）への直接 push |
| 秘密情報 | 認証情報・トークンの生成・ローテーション・露出 |

### 2. 要件が一意に定まらない

- 解釈が複数成り立ち、選択によって成果物が大きく変わる
- 受け入れ条件（DoD）が示されず、完了の判定基準を作れない
- 実装が依存する、「要確認」「TODO」「残課題」と明記された未確定項目
- 既存の設計仕様（業務概要・承認ルート・ユーザーロール・画面設計など）と矛盾する指示

### 3. 安全・法令・コンプライアンスに関わる

- 法令で定めのある処理ロジック（記録義務・帳票など）の変更
- 承認ルート・承認閾値の変更
- 勤怠・個人情報など機微データの取扱いの変更
- アクセス権限・ロール境界の変更

### 4. コスト・影響範囲が大きい

- 課金・有料リソースの新規作成や利用
  - 要件で対象と金額が承認済みでない限り停止
- 技術選定・アーキテクチャの新規決定や変更（ADR 相当の判断）
- 広範囲に波及する破壊的リファクタ、依存の大幅な更新

## 自走してよい（PROCEED）

- 保護ブランチ外の作業ブランチでの実装・テスト・リファクタ
- 設計・受け入れ条件が一意に定まっている機能の実装
- lint・型・テスト・build を緑にする修正
- ローカル・隔離環境内での実行と検証
- 既存方針に沿うドキュメントの追記・整形

## 停止するときの伝え方

何を・なぜ確認したいか・選択肢と推奨を、1 度のやり取りで提示する。

## 強制レイヤーとの関係

- 本境界は Advisory（読んで従う層）
  - AI が読んで判断に反映することを前提とし、これが唯一の防波堤になりうる想定で運用する
- `.claude/settings.json` の deny・hooks で同種の操作（force-push、`.env` 読取、`rm -rf`、保護ブランチへの直接 push 等）を機械的に拒否する設定がプロジェクトにあれば、それは本境界を裏打ちする第二の防波堤として働く
  - 無くても本境界の実効性はこの文書の遵守だけで成立する
  - あってもこの文書の内容は変わらない（対象操作の一覧を保守するのは設定・hooks 側）
