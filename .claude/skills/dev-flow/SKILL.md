# dev-flow — feature 開発フローのオーケストレータ

機能開発を受けてから PR がマージ可能になるまで、各スキルを順に呼んで自走させる。2 層アーキテクチャの上層で、自身は実作業をしない。呼ぶ順・分岐点・停止位置だけを持ち、各スキルの中身は再説明しない。

不可逆な操作・課金・法令/安全/承認・権限・要件の曖昧さに関わる判断は、実行前に止めて確認する。迷えば止める（[ESCALATION.md](ESCALATION.md)）。

## 到達点で止まる位置を決める

要件・設計の合意とは別の軸である。未指定なら着手前に確認する。

- 検討のみ / コミットまで / マージ可能まで の 3 つ
- 質問できない `/loop`・スケジュール文脈では、最も巻き戻しやすい「コミットまで」（push しない）で止める

## 主軸（feature モード）

1. 着手前チェック
   - `git status` → クリーンなら main を最新化 → `feature/<topic>` ブランチ（非 ASCII 禁止）を切る
   - クリーンでない/要件が曖昧なら止めて確認
2. 要件確定［人ゲート］
   - 作る範囲が曖昧なときだけ `requirements-define`
   - 固まっていれば飛ばす
3. 周辺探索
   - 触る対象の周りを薄く見る
   - 範囲は不可逆性に比例（DB スキーマ・共有部品・公開 API は広く、葉のロジックは最小）
4. 設計
   - 既存実装に倣う
   - UI を含むならデザイン確定の鎖（参照デザイン → HTML/CSS 確定 → 実装後の見た目レビュー）を通す
5. 設計提案［人ゲート］
   - 後戻りしにくい選択肢があるときだけ `design-proposal`
   - 一意なら飛ばす
6. 実装
   - 既存実装に倣う
   - UI は確定 HTML/CSS を対象フレームワークへ移す
   - TDD（Red→Green→Refactor）
7. テスト・lint・build
   - プロジェクトのコマンドを成功させる
   - 決定的コマンドはスキルにしない
8. 自己レビュー［常設ゲート］
   - push 前に別コンテキストで `/code-review`（正確性バグ・簡素化）を 1 パス
   - 設計・規約に効く差分なら加えて `convention-review`
   - 些細な差分では飛ばす
9. 提出
   - commit→push→PR
   - 分類ラベルを付ける
   - Issue なしタスクは `feature/` 経路で代替し、受け入れ条件を PR 本文に明記
10. マージ可能まで
    - PR 作成後に `/loop` で `pr-review-loop` を回す
    - CI 失敗対応と指摘の規約還元を内包

人ゲートは自動で正否を判定できない 2 段（要件・設計）に限る。実装段以降に足さない。

## 分岐点 — 横断インフラは先行 PR へ

複数の画面・機能が再利用する土台（共通スタイル層・トークン・テスト基盤・サービス層ヘルパ等）が混ざるときは、要件 PR に同梱せず先行の独立 PR に切り出す。土台が無ければ分割しない。提出の前に見極める。

## bug モード

不具合起点は主軸の前段に `reproduce-diagnose` を差し、後半（設計〜マージ可能）を feature の主軸と共有する。重複実装しない。

1. 着手前チェック — feature の主軸と同じ
2. 再現と原因局所化
   - `reproduce-diagnose` で再現手順・原因の所在（file/line）・直す/直さないの判断材料・修正方針候補を得る
   - これが周辺探索（3）と設計（4）の入力を兼ねる
   - 再現できなければ止めて確認
3. 判断材料を人ゲートへ渡す — 直す/直さないの確定は要件ゲート、修正方針の承認は設計提案ゲートへ
4. 以降は feature の主軸と同じ

本番データ・承認ルート・権限に触れる再現/修正は、実行前に止めて確認する（[ESCALATION.md](ESCALATION.md)）。
