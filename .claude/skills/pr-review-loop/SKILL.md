# pr-review-loop — PR レビューの自律対応ループ

PR に付くレビューを検討・対応し、「あとは人間がマージするだけ」まで持っていく。即座にはレビューされないので、待機は `/loop` に任せる。レビュー状態は毎回 PR から読み直し、会話の記憶に頼らない。

ラベル（Actionable / Nitpick 等）でなく中身で判断する。特定レビュアーの消化でなく、全レビュアーが納得する状態にする。

## 起動

`/loop /pr-review-loop [PR番号]` で起動する。PR 番号を省くと現在のブランチの PR を使う。以降の待機・再起動は `/loop` が回す。

## 境界

- 保護ブランチにいたら即中断して報告（設定はプロジェクトの規約）
  - 直接 push・`--force`・`--no-verify`・`--amend` はしない
- 重大な指摘、不可逆な操作・課金・法令/安全/承認・権限・要件の曖昧さに触れる判断は、自動対応せず止めて確認
- マージはしない

## ループの判定

`scripts/read-reviews.sh [PR]` でレビューの 3 所在（review 本文・インラインコメント・サマリ）を読む。最新レビューが現在の HEAD を対象にしているかで状態を分ける。

| 状態 | 条件 | 行動 |
|------|------|------|
| 待機中 | HEAD をまだレビューしていない | 何もせず次のポーリングへ |
| 対応 | HEAD へのレビューに未対応の指摘が残る | 検討・対応して push、次のポーリングへ |
| 完了 | 未対応の指摘が無く、CI 全成功・マージ可能 | ループを終え人間に渡す |
| 要確認 | マージ競合・無関係な CI 失敗・設計判断を要する指摘・6 巡超過 | ループを終え状況を添えて確認 |

CodeRabbit が付く PR は [CODERABBIT.md](CODERABBIT.md) に従う。

## 指摘への対応

各指摘を中身で評価する。採否どちらも別の場所にまとめない。

- インラインコメントには `scripts/reply.sh <comment_id> <本文>` を使う
- review 本文・PR コメントは種類が異なり同じ endpoint に返信できないため、`gh api` で対応する種類のコメント作成 endpoint を使う

- 妥当な指摘
  - 対応
  - 相違がなければ返答不要
- 対応しない指摘
  - 当該スレッドにて理由を返答
- スコープ外修正
  - 別 PR を検討
  - 当該 PR で「ついで修正」しない
- 再発しうる・全体に効く指摘
  - この PR で対応しつつ、別の独立 PR で規約・docs・スキルへ還元
  - スレッドに「別 PR に切り出す」と明記して返す
  - 規約変更は独断で確定せず、提案と根拠を PR 本文に書いて人間の承認に委ねる

コミットは話題ごとに分ける。修正の流儀（テスト・ビルド・lint・push・PR 本文の差し替え）はプロジェクトの提出フローに従う。

## CI 失敗への対応

レビューと並行して解消する。本筋と無関係でも放置しない。

- 原因（file/line・ルール）を特定してから直す
  - 憶測修正で回さない
- 機密値は CI ログに出さない
  - 場所＝file/line だけ出す
- 本筋と無関係な失敗は別 PR に切り出す
  - 本筋にノイズコミットを溜めない

## 待機と完了

- 待機ターンは状態確認だけにとどめ、余計な作業やコメントをしない
- ポーリング間隔（`ScheduleWakeup` の `delaySeconds`）の目安は、初回 360 秒・以降 330 秒・再レビュー直後 240 秒
  - 300 秒ちょうどはキャッシュ最悪点なので避ける
- 完了時は次のポーリングをスケジュールせず、要点とマージ可否を報告
  - 判定表の「完了」条件を満たして初めて完了と言う
