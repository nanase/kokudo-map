# convention-review — 規約・既存コードの慣習と diff を突き合わせる

どこを直すと「このリポジトリの書き方」に揃うかを file/line で挙げる定性レビューである。正確性バグ・見た目・lint/typecheck/formatter が拾うもの（整形・import 漏れ・型エラー）は見ない。

設計・規約に効く差分（サービス／ロジック層・新規モジュール・構造や依存方向の変更）を push 前に確かめたいとき回す。些細な差分（ドキュメント・整形・依存の更新）は対象外とする。自己確認は甘くなるので、回すと決めたら第三者に通す。

## 2 層で見る

条項違反（明文）と既存の書き方からの逸脱（暗黙）は別物である。両方を別々に見る。第 2 層のほうが広い。従うべき方針の多くは条項でなく既存コードに宿るためである。

| 層 | 正にするもの | 拾うもの |
| --- | --- | --- |
| 第 1 層 明文規約 | CLAUDE.md・ADR・領域別規約の条項 | 条項違反。総当たりで決定的に拾える |
| 第 2 層 既存慣習 | 同領域の既存実装 | 条項に無い崩れ＝既存の書き方からの逸脱 |

## 手順

### 1. 材料をそろえる

- 対象の diff
  - base との差分・変更行に絞る
  - 既存の問題は見ない
- 効く明文規約の出典をファイルパスで集める
  - 中身は写さず参照
  - ルート/領域別の `CLAUDE.md`・`AGENTS.md`、該当 ADR、触れたファイルのコメント・lint ignore
- 同領域の既存実装
  - 粒度・命名・配置・依存方向・エラーの扱いの慣習を控える

### 2. 第 1 層 — 明文規約を総当たりで照合する

集めた条項を上から順に潰す。条項ごとに「diff に効くか → 効くなら適合しているか」を判定し、効かない条項は「該当なし」と明示する。違反は条項テキストと diff の該当箇所を並べて出す。

> 例: `<領域別 CLAUDE.md>「time.Now() は timezone を明示」 vs service/foo.go:42 直書き … 違反`

事前に渡された指摘は、総当たりの代わりにせず、最後の答え合わせに使う。

### 3. 第 2 層 — 既存の書き方への準拠を第三者に見させる

別コンテキストのサブエージェントを Agent ツールで起動する。規約・既存パターンへの適合判断は高度な推論なので、Opus 系（`claude-opus-4-8` 以降）を明示する。実装意図・弁護は渡さず、diff・同領域の既存実装・第 1 層の違反リストだけを判断材料として渡す。プロンプトに必ず含める:

> あなたは実装会話を持たない第三者のレビュアーです。基準は一般論の設計の良し悪しでなく、このリポジトリの既存実装です。(1) 違反リストに載っていない崩れ、(2) 既存実装の書き方（粒度・命名・配置・依存方向・エラーの扱い）に倣えているか、を見て良い点と直したい点を挙げてください。各指摘は file/line・関数/型を特定し、根拠が「規約」か「既存慣習」か、「直すべき差」か「意図的な逸脱」かを明示してください。正確性バグと見た目、linter が拾う整形、具体的な直し方は挙げず、観察に徹してください。

### 4. 仕分けして反復する

第 1 層・第 2 層の指摘を等しく仕分けし、残差が落ち着くまで 2〜3 を回す。

- 既定は「直すべき差」
  - 直して再照合
- 「意図的な逸脱」は理由を PR 本文に 1 行記録
  - 記録する内容は file/line / 内容 / 理由
  - スコープ外・段階移行中・コメント宣言済みなどに限る
- 規約への疑問・規約と既存コードの矛盾は、勝手に直さず確認へ回す

## やってはいけないこと

- 規約を発明
  - 「規約違反」と言うなら条項テキストと出典を示す
  - 明文に無いものは「既存慣習」と明示
- 自分好みの設計に引き寄せる
  - 基準は既存実装
  - 一度きりの書き方や好みの差は挙げない
