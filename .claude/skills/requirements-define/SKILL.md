# requirements-define — 設計前に作る範囲を人と確定する

要望を受けたら、設計に入る前に「何を作って何を作らないか」と受け入れ条件を人と詰める。人が数十秒で答えられる粒度に絞る。実作業（設計・実装）はしない。

作る範囲が正しいかは test も AI レビューも判定できない。だからここに人ゲートを 1 つ置く。設計意図は設計段のゲートが、実装は test・AI レビューが見る。

## 発動するか — 作る範囲が曖昧なときだけ

要望の文面でなく、作る範囲が一意に決まっているかで決める。

- 範囲・受け入れ条件に解釈の幅がある → 発動して詰める
- 具体的で一意・既存実装に倣うだけ・些細 → 発動しない
  - 前提を一行 FYI に留めて次段へ渡す
- 迷ったら発動させる（範囲のズレは後段ほど高くつく）

## 質問のしかた

答えによって作る物が変わる問いだけを尋ねる。実装詳細・命名のような、作る物が変わらない問いは尋ねない。

- AI の前提を示し、確認・訂正してもらう形（「〜という想定で合っていますか」）
- yes/no か短い選択で答えられる形
  - 自由記述を求めない
- 範囲の境界（含む／含まない）と、明らかでない受け入れ条件を優先
- `AskUserQuestion` で尋ねる
  - 数問までとし、長いインタビューにしない

範囲と受け入れ条件が設計に着手できるだけ固まったら止める。細部は設計・実装で決める。

## 提示テンプレート

```text
要望を受けました。設計に入る前に、作る範囲を確認させてください。

想定（合っていれば yes、違えば訂正してください）:
- やる: <作るもの>
- やらない: <今回作らないもの>
- 受け入れ条件: <満たせば完成と言える条件>

この範囲で設計に進めてよいですか。
```

## 出力

確定した範囲を短いリストで返す。呼び出し元が設計の入力にする。

- やる: 今回作るもの
- やらない: 今回作らないもの（範囲外と明示）
- 受け入れ条件: 満たせば完成と言える条件

固まらなければ、不足している 1 点だけ聞き返す。
